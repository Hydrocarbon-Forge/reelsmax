# Reelsmax — FIX BRIEF (C6 audit, 2026-10-05)

C6 audited the Product A build. **The lane layer is not real.** Your
verify suite "passed" because it tested a simulated state machine, not
video. Evidence from the audit (verify each of these yourself — if any
is wrong, say so):

## Root causes (all verified in code)

1. **`server.py` contains ZERO browser control.** 0 matches for
   subprocess/Popen/websocket/playwright/CDP. A "lane" is an in-memory
   dict; no lane plays anything. Nothing is actually running YouTube.
2. **Wall tiles render `youtube-nocookie.com/embed/<id>` iframes fed
   from the hardcoded `DEFAULT_FEEDS` list** (web/app.js:159,207). 28 of
   40 sampled seeded IDs return 404 to oembed → dead tiles. This is a
   canned list, not "the next short on YouTube", so req. #2 (space =
   next short ON YOUTUBE) and #5 (different FEEDS) are unmet by
   construction.
3. **Per-lane cookies do not exist.** `run.sh` opens ONE chromium window
   on the wall page with ONE shared profile
   (`snap/chromium/common/reelsmax-wall-profile`). The
   `data/profiles/lane_N/` dirs hold a fabricated `session.json` (fake
   UA "Reelsmax/1.0") that nothing ever reads. No feed divergence.
4. **RAM numbers are fabricated.** `server.py:297` —
   `lane_rss = 35.0` is a hardcoded fallback used when no browser
   processes are found (i.e. always, since none exist). Your "12 lanes =
   442 MB, ~35 MB/lane" is arithmetic on a constant, not measurement.
5. Autoplay-with-audio was never actually demonstrated — the whole
   layer it would have lived in doesn't exist.

**Keep** (it's good): the UI shell (index.html/app.js/style.css grid +

(/api/state,/add,/remove,/next,/pause_all,/mute_all,/lane/<id>/next),

**Delete/replace:** `DEFAULT_FEEDS` and all fake seeded video IDs, the
fabricated `session.json`/`cookies.txt`/`history.json` profile files,
the `35.0` fallback, and the verify suite's ability to pass without
real lanes (it must be impossible).

## What a real lane is (architecture — implement this)

One lane = ONE real chromium process (chromium IS installed at
`/usr/local/bin/chromium` — verify `chromium --version` first):

- `chromium --user-data-dir=<repo>/data/profiles/lane_<id> --app=URL`
  with `--window-size`/`--window-position` from the computed grid,
  `--autoplay-policy=no-user-gesture-required`, plus mobile UA
  (`--user-agent`) so youtube.com/shorts gives the single-column shorts
  feed (test desktop vs mobile yourself and use whichever makes
  next-short reliable).
- **Per-lane cookie identity** = the per-lane `--user-data-dir` (fresh
  dir = fresh anonymous feed). This is the real req #5.
- **Grid = the lanes themselves.** N lanes → auto-fit rows×cols of 9:16
  tiles from the ACTUAL `xrandr` geometry (not hardcoded 1280x800);
  each lane window is placed/sized by that computation. Adding/removing
  a lane recomputes and resizes/moves ALL lane windows (CDP
  `Browser.setWindowBounds` works on already-running windows; flags
  work for new ones). Zero scrollbars is inherent (windows, not a page).
  The 8905 web page becomes the CONTROL SURFACE (control bar + lane list
  + live RAM telemetry + add/remove), optionally shown in its own window.
- **Control channel = CDP.** Launch each lane with
  `--remote-debugging-port=<unique port, e.g. 9220+id>` (or a single
  shared pipe per process — your choice), `pip install
  websocket-client` is fine. The server keeps a CDP session per lane.
- **Spacebar = next short on YouTube, unison:** drive the shorts UI's
  own next behavior via CDP (swipe/touch `Input.dispatch*` OR read the
  next feed item and navigate — find what actually works and USE it).
  Verify: capture each lane's current video id before and after; every
  lane's id must change.
- **Pause / mute all:** per-lane CDP (set `video.paused` /
  `video.muted` via `Runtime.evaluate`, or media keys) — verify the
  effect reads back true on every lane.
- **Audio:** lanes start UNMUTED and playing. If the host has no audio
  device, verify playback state via CDP instead (`document.querySelector('video').paused === false`, `muted === false`, readyState) and state which method you used in the report.

## Verification (the suite must make faking impossible)

`verify_product_a.py` must prove, per lane, via live CDP:
